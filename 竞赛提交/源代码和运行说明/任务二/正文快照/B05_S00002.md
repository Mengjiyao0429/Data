## 正文
After #184 I went through the firmware source (`main/` and the build configuration, at 7058186) with AI coding agents, looking for similar problems. This is the list of what came out of it. **How to read this:** everything below is from reading the code and the ESP-IDF v5.5.2 sources. Nothing was reproduced on a device, so each item may turn out to be wrong or unreachable in practice. Items 1-11 were checked a second time against the code; the items under "Suspicions" were not. Line numbers refer to 7058186. The SNTP findings from the same review are in #186. **My question:** for which of these, if any, would you like a pull request? I would rather not send a pile of PRs you did not ask for, and I can only test on a Tidbyt Gen2. ## Can crash or hang 1. **`gfx.c:661` - result of `WebPAnimDecoderGetNext()` is not checked.** On a frame decode error libwebp returns 0 without setting `pix`/`timestamp` and without advancing, so `display_draw()` gets an uninitialised pointer (first frame), or the loop redraws the last frame forever and HTTP mode never fetches again (later frame). Trigger: a WebP whose container parses but whose frame data does not decode, or out of memory inside the decoder. 2. **`ap.c:913` and `:1002` - `esp_restart()` inside an HTTP handler.** `esp_restart()` runs the shutdown handlers in the calling task; `wifi_shutdown()` -> `ap_stop()` -> `httpd_stop()` then waits for the server thread to stop, which is the calling thread. If I read this right, "Save" and the firmware upload hang instead of rebooting. This would be very visible, so please tell me if it simply works for you. 3. **`main.c:1023` - `Tronbyt-Image-URL` header is saved and followed by a reboot without checks.** The result of `nvs_set_image_url()` is ignored and the value is not compared with the current one: a URL longer than 128 characters, or a server that sends the header on every response, gives a save/reboot loop; an empty value clears the URL. 4. **`gfx.c:565-580` with `:651` - gfx task spins without a delay while `isAnimating == -1`.** `draw_webp()` returns immediately in that state and `gfx_loop` calls it again at once, until a new image arrives. Triggers: tap in WebSocket mode, `"immediate": true` arriving after its image was loaded, a tap in HTTP mode while fetches fail. 5. **`main.c:279` and `:1018` - a second OTA task can start while one is running.** There is no in-progress flag; in HTTP mode the loop keeps fetching during the update and starts another task if the header is still sent. ## Silently does not work 6. **`wifi.c:123` - SSIDs of exactly 32 bytes and 64-character PSKs lose their last character.** `nvs_get_ssid()`/`nvs_get_password()` always write a NUL at `buf[max_len-1]`, and they are called with the exact-size fields of `wifi_sta_config_t`. 7. **`remote.c:190` - the body of an HTTP redirect ends up in the image buffer.** `HTTP_EVENT_ON_DATA` is also dispatched for the 3xx response and `state->len` is not reset, so the buffer is redirect body + WebP. 8. **Pixoticker (`CONFIG_SPIRAM=n`) versus `MALLOC_CAP_SPIRAM`-only allocations** in `remote.c:176`/`:224`, `main.c:538`, `ap.c:748`/`:923`. Without a PSRAM heap these return NULL every time, so that build could neither fetch an image nor save from the portal. `ap.c:670` already uses `heap_caps_calloc_prefer()` with a fallback. 9. **`gfx.c:615` - `dwell_us = app_dwell_secs * 1000000` overflows `int`** above 2147 s. WebSocket mode allows up to 3600; the image is then never drawn. ## Minor 10. **`main.c:820` - out-of-bounds read** in the "API key: ...%s" log line when the key is shorter than 4 characters (`api_key + key_len - 4`). 11. **`ap.c:478` - the stored image URL is written into the portal page unescaped** inside `value='...'`. An apostrophe truncates the field on the next save; markup is injected into the page. ## Suspicions (not double-checked) - `syslog.c:130`: the log hook calls `sendto()` from whichever task logs.
