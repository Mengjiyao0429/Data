## 正文
As part of an investigation into clangd misbehaving in my VS Code instance (see the end of this post if you want that context), I'm trying to cross-compile a super simple program using clang 18.1.3 on Ubuntu 24.04, for arm-none-eabi . My main.cpp is as simple as can be: int main(int, char**) { return 0; } I have downloaded the relevant ARM GNU Toolchain for my Ubuntu host, which is arm-gnu-toolchain-15.2.rel1-x86_64-arm-none-eabi.tar.xz . As per documentation I've seen online, I need to pass --sysroot=/path/to/toolchain/arm-none-eabi to clang (making sure not to forget that arm-none-eabi suffix to the main toolchain directory), and it should discover the correct binaries to use for compilation. My command, therefore, is this: clang --verbose \ --target=arm-none-eabi \ --sysroot=${HOME}/Desktop/arm-gnu-toolchain-15.2.rel1-x86_64-arm-none-eabi/arm-none-eabi \ -o executable \ main.cpp This command fails, with the error: clang: error: unable to execute command: Executable "ld.lld" doesn't exist! clang: error: ld.lld command failed with exit code 1 (use -v to see invocation) Amongst the toolchain binaries I can see ld and ld.bfd , but no ld.lld . Looking into the logs produced by --verbose , I'm also not sure that clang is correctly detecting the include directory from the toolchain. I see these messages: ignoring nonexistent directory "/home/jonathan/Desktop/arm-gnu-toolchain-15.2.rel1-x86_64-arm-none-eabi/arm-none-eabi/include/c++/v1" ignoring duplicate directory "/usr/lib/llvm-18/lib/clang/18/include" #include "..." search starts here: #include <...> search starts here: /usr/lib/llvm-18/lib/clang/18/include /home/jonathan/Desktop/arm-gnu-toolchain-15.2.rel1-x86_64-arm-none-eabi/arm-none-eabi/include End of search list. It seems that in the sysroot, clang is expecting include/c++/v1 , when the actual directory I see on my machine is include/c++/15.2.1 . I have also seen recommendations to add --gcc-toolchain=/path/to/toolchain (without the same suffix as the sysroot path), but if I do this then clang just logs that it is an unused argument. My question is: why is clang not able to determine either the correct include directory, or the linker binary? Are there extra parameters I need to pass to this call? It's proven quite difficult to find adequate specifics online for using clang with the ARM toolchain. The LLVM cross-compilation docs even states that, having extracted a cross-compilation toolchain from a zip like I did: if no additional headers or libraries are needed ... Clang will find all binaries it needs Implying that I shouldn't need to specify any paths manually. (Perhaps this assumption is mistaken, though.)
