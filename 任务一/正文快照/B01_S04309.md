## 正文
I'm working on a Linux application that communicates with a HART modem over a serial port , specifically using a FTDI USB-to-serial modem . The application uses Boost.Asio for asynchronous serial communication. In the real application, I’ve observed a rare issue where the last byte of an incoming message — the checksum byte — is sometimes received as 0x00 instead of the correct value. For example, when the device sends {0x0A, 0x0B, 0x0C} , the application receives {0x0A, 0x0B, 0x00} . To investigate, I created a simplified test program (not using Boost.Asio) that mimics the behavior with low-level system calls. Here's a minimal reproducible example that replicates the issue. ✅ Working version (non-blocking read with sleep): int fd = open(comPort.c_str(), O_RDWR | O_NOCTTY | O_NONBLOCK); while (true) { uint8_t byte; ssize_t n = read(fd, &byte, 1); if (n > 0) { SPDLOG_INFO("Read byte: 0x{:02X}", byte); } else if (n == -1 && errno != EAGAIN) { SPDLOG_ERROR("Read error: {}", strerror(errno)); break; } else { std::this_thread::sleep_for(std::chrono::milliseconds(1)); } } close(fd); This version works reliably — all bytes are received correctly, including the checksum. ❌ Problematic version (using poll() ): int fd = open(comPort.c_str(), O_RDWR | O_NOCTTY | O_NONBLOCK); while (true) { uint8_t byte; ssize_t n = read(fd, &byte, 1); if (n > 0) { SPDLOG_INFO("Read byte: 0x{:02X}", byte); } else if (n == -1 && errno != EAGAIN) { SPDLOG_ERROR("Read error: {}", strerror(errno)); break; } else { pollfd pfd{}; pfd.fd = fd; pfd.events = POLLIN; int ret = poll(&pfd, 1, -1); if (ret == -1) { SPDLOG_ERROR("poll() error: {}", strerror(errno)); break; } else if (ret > 0 && (pfd.revents & POLLIN) == 0) { SPDLOG_ERROR("revents[{}] != POLLIN[{}]", pfd.revents, POLLIN); break; } // No delay here } } close(fd); This version works most of the time, but very occasionally, the last byte of a message is received as 0x00 . It usually happens on the checksum byte , which leads to message validation failures. ✅ Adding a short delay after poll() fixes the issue: // Inside the poll() block std::this_thread::sleep_for(std::chrono::microseconds(1)); Adding even a 1-microsecond delay after poll() consistently prevents the issue. All bytes, including the checksum, are received correctly. Additional Context ❌ The Boost.Asio code which works similar as the Problematic version : asio::io_context ioContext; asio::serial_port serial(ioContext); serial.open(comPort); serial.set_option(asio::serial_port_base::baud_rate(1200)); serial.set_option(asio::serial_port_base::character_size(8)); serial.set_option(asio::serial_port_base::parity(asio::serial_port_base::parity::odd)); serial.set_option(asio::serial_port_base::flow_control(asio::serial_port_base::flow_control::none)); serial.set_option(asio::serial_port_base::stop_bits(asio::serial_port_base::stop_bits::one)); uint8_t byte; asio::error_code ec; while (true) { size_t len = asio::read(serial, asio::buffer(&byte, 1), ec); if (ec) { SPDLOG_ERROR("Error reading from serial port: {}", ec.message()); break; } SPDLOG_INFO("Read byte: 0x{:02X}", byte); } serial.close(); 🔍 My Questions Why does this happen? Why does reading immediately after poll() sometimes return 0x00 instead of the actual transmitted byte? Is this a known issue or race condition when using poll() with non-blocking serial I/O on FTDI USB serial devices (or in general)? What is the correct or recommended way to handle this? Should I always add a short delay after poll() ? Or is there a more robust approach — especially when using Boost.Asio? Any insights — especially from those familiar with FTDI devices, Boost.Asio internals, or Linux serial port quirks — would be greatly appreciated!
