## 正文
I often see advice recommending that SqlConnection and SqlTransaction should be disposed of as soon as you're done using them, and that you should not rely on the garbage collector for cleanup. In our case, we are building an ASP.NET Core Web API and designing how our service layer interacts with the repository layer. We're considering two different approaches to managing SQL Server connection lifetimes. Current pattern: explicit using statement inside the service: public class JobService : IJobService { public async Task SomeJobMethodAsync() { using (var connection = new SqlConnection("...")) { await connection.OpenAsync(); // Do some work with the connection } // connection disposed here } } This follows the guidance of disposing the connection immediately after use. Proposed pattern: encapsulate SqlConnection in an injected class: public class JobService : IJobService { private readonly ISqlManager _sqlManager; public JobService(ISqlManager sqlManager) { _sqlManager = sqlManager; } public async Task SomeJobMethodAsync() { _sqlManager.PerformOperation(); // does work using an internally-held connection // no explicit disposal here } } public interface ISqlManager : IDisposable { void PerformOperation(); } public class SqlManager : ISqlManager { private readonly SqlConnection _connection; private readonly SqlTransaction _transaction; public SqlManager(string connectionString) { _connection = new SqlConnection(connectionString); _connection.Open(); _transaction = _connection.BeginTransaction(); } public void PerformOperation() { using (var cmd = _connection.CreateCommand()) { cmd.Transaction = _transaction; cmd.CommandText = "..."; cmd.ExecuteNonQuery(); } } public void Dispose() { _transaction?.Dispose(); _connection?.Dispose(); } } The key idea here is that the SqlManager class holds and manages the connection and transaction internally, and it's injected into the service using DI. It implements IDisposable , and will be disposed either manually or by the DI container (depending on lifetime configuration). My question : does the second pattern — where the connection and transaction are encapsulated inside a disposable class that is injected into the service — still satisfy the principle of "disposing the connection/transaction as soon as you're done with them"? In other words: do you have to use a using statement every time? Or is it acceptable to rely on the Dispose() method of an injected class that manages the connection internally? I'm not asking for a review of architectural layering or DI patterns — I'm just trying to understand whether the disposal mechanism shown in the second approach is considered safe and correct in terms of proper ADO.NET resource management. I also enjoy learning about systems at a low level whenever possible. Any links regarding to the disposal process are also very much appreciated. When injecting a disposable class into a service class, I can confirm the Dispose() method is called with no delay -- it happens right after the controller returns the data to the client. My question isn't about whether to dispose, but about the timing of the disposal -- specifically for SqlConnection .
