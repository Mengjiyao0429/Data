# Can RegisterApplicationRestart relaunch an MSIX app after ExitProcess(0) following a StoreContext update?

## 正文
I am reviewing a Windows restart flow in a Flutter desktop app packaged as MSIX and intended for Microsoft Store distribution. The app uses a custom Flutter Windows plugin; there is no external updater or separate installer. The forced-update path is: Dart calls startUpdate(immediate: true) through a MethodChannel . The native C++ plugin obtains StoreContext::GetDefault() , associates it with the app HWND through IInitializeWithWindow , and calls GetAppAndOptionalStorePackageUpdatesAsync() . It awaits RequestDownloadAndInstallStorePackageUpdatesAsync(updates) and reports PackageDownloadProgress to Dart. When StorePackageUpdateResult::OverallState() is Completed , it executes the following code: result->Success(flutter::EncodableValue(true)); if (immediate) { HRESULT hr = RegisterApplicationRestart( nullptr, RESTART_NO_CRASH | RESTART_NO_HANG); // The production code will log hr, but currently treats restart // registration as best-effort. ExitProcess(0); } No restart command-line arguments are registered. A relaunched instance is expected to follow the normal startup path. For a non-forced update, the same Store APIs are used with immediate == false , but the process is left running. I am unsure whether the forced path relies on behavior that RegisterApplicationRestart does not provide: The documentation says that a desktop app should register before an installer attempts to shut it down, with WM_QUERYENDSESSION being the last opportunity. The Store update documentation says that, under normal circumstances, the app may terminate while RequestDownloadAndInstallStorePackageUpdatesAsync installs the update. The restart documentation describes automatic restart for a crash, hang, system restart, or installer-driven update. It does not clearly say that a clean, app-initiated ExitProcess(0) triggers a registered restart. For a full-trust packaged Win32/Flutter app: Can RegisterApplicationRestart cause a relaunch after this explicit clean ExitProcess(0) , merely because a Store update completed immediately beforehand? Is the code after an OverallState::Completed result guaranteed to run, or can package deployment terminate the app before the async operation returns? Should the supported sequence instead be: register before RequestDownloadAndInstallStorePackageUpdatesAsync , save state/handle WM_QUERYENDSESSION and WM_ENDSESSION , and let Store deployment close and relaunch the process? Does the documented 60-second minimum runtime for automatic restart apply to an installer/Store-update restart too? I am looking for the documented restart semantics and the supported call order, rather than a recommendation for a third-party updater.
