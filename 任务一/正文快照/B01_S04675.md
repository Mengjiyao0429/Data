## 正文
We are currently benchmarking OceanBase 4.3.3 for a large-scale RAG application. Our main vector table is partitioned by user_id (Hash partitioning) across 3 nodes to handle high-concurrency ingestion. We are using the VSAG index for vector similarity search. In a distributed setup, I’m concerned about how the ANN_SEARCH is executed when a query doesn't include the partition key, or when it covers multiple partitions. Here is a simplified version of our query: SQL SELECT doc_id, doc_content FROM ob_vector_table ORDER BY APPROX_DISTANCE(vector_col, [0.1, 0.2, ...]) APPROX_TOP 10; From what I understand about distributed vector databases, there's usually a trade-off between "Local Top-K" and "Global Top-K." If each partition only searches its local VSAG index and returns 10 results, the final merged 10 results might not be the true global top-10, leading to a drop in recall. My question is: Does OceanBase's execution engine automatically increase the TOP-K value during the local search phase on each node (similar to "over-fetching") to compensate for potential recall loss before merging the results at the coordinator level? Or is there a specific session variable (like ob_vector_search_limit_factor or similar) we should tune to balance latency and recall accuracy when searching across multiple partitions? We are seeing a slight recall dip compared to a single-node MySQL/pgvector setup, and I want to know if this is an expected behavior of the distributed graph-based index or if it's a configuration issue.
