# When should I use GraphRAG instead of traditional vector-based RAG?

## 正文
I’m building a RAG application where users ask questions over a collection of documents. The traditional architecture I’m considering is: Split documents into chunks Generate embeddings Store the embeddings in a vector database Retrieve the top-k most similar chunks Pass those chunks to an LLM This works reasonably well for questions where the answer is contained in one or a few semantically similar chunks. However, I’m running into questions that require connecting information across multiple entities or documents. For example: “Which customers are affected by vulnerabilities in products that depend on library X?” The relevant information may be distributed across several records: Customer -> uses -> Product Product -> depends_on -> Library Library -> has -> Vulnerability A vector search can retrieve documents mentioning the customer, product, library, or vulnerability, but it does not explicitly perform the multi-hop relationship traversal. I’ve been looking at GraphRAG approaches where the retrieved context includes a knowledge graph and graph traversal in addition to, or instead of, vector similarity search. My questions are: What types of queries are a good indication that GraphRAG is preferable to standard vector RAG? Is GraphRAG typically used as a replacement for vector retrieval, or as an additional retrieval step? How do production GraphRAG systems decide which subgraph to retrieve without sending an excessively large graph to the LLM? Are there established ways to measure whether GraphRAG actually improves retrieval quality compared with vector RAG, especially for multi-hop questions? I’m particularly interested in architectural or implementation differences rather than comparisons between specific database products.
