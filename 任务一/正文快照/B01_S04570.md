## 正文
I've been struggling on this problem for the past few hours and I think it's driving me insane, so I thought I'd ask here. I've been working on a Windows application. It needs to open a window so it's compiled under the Windows SubSystem ( /SUBSYSTEM:WINDOWS flag in MSVC), this also means that it doesn't open a terminal by default, but I do want one to print stuff to while I'm working on it. The Windows API provides the solution for this: the AllocConsole function which, as the documentation says, "allocates a new console for the calling process". After calling it, it does indeed open a console window, and I'm able to printf to it after calling freopen like this: (Note that freopen is needed because we need to redirect whatever we write to stdout to "CONOUT$" etc.) bool AttachCon() { if (AllocConsole() == FALSE) { return false; } FILE *tmp; _wfreopen_s(&tmp, L"CONIN$", L"r", stdin); _wfreopen_s(&tmp, L"CONOUT$", L"w", stdout); _wfreopen_s(&tmp, L"CONOUT$", L"w", stderr); return true; } The problem arises when trying to print wide-character strings. By default the Windows terminal uses the code page 850 character encoding, which is not good for what I need. After searching online you can quickly see that the solution is an obscure call to _setmode with the mode parameter set to _O_U16TEXT , like this: _setmode(_fileno(stdin), _O_U16TEXT); _setmode(_fileno(stdout), _O_U16TEXT); _setmode(_fileno(stderr), _O_U16TEXT); As far as I understand, this basically tells the functions that print to the screen that the text they will receive is encoded in whatever is specified by the user, and that it doesn't actually change the code page in the terminal ( GetConsoleCP always returns 850). Those functions then translate the strings from one encoding to the other automatically. Here is where the problem lies: trying to do the above on a console application works (as long as the /utf-8 flag is specified, more on that later), but it does not in the Desktop application. The output I get when trying to print L"Test à" is T e s t Ó : T e s t Ó Note that à is 0x00E0 in UTF-16, and that Ó is also 0xE0 in code page 850 . Also there are weird spaces between every character for some reason (I'm assuming it's the second byte of the UTF-16 character). This is what I've tried and observed so far on my machine: By default a wchar_t string uses UTF-8, this can be changed by compiling the project using the /utf-8 flag (which as far as I can tell can only be set by manually setting it in Project Properties --> C/C++ --> Command Line in Visual Studio), doing this sets the encoding to UTF-16 (seems kind of backwards to me?) _setmode returns the previous translation mode. When calling it a first time it returns 0x4000 which corresponds to _O_TEXT - text (translated) , and the second time it returns 0x10000 , which should correspond to _O_U16TEXT - UTF16 no BOM (translated) , since that's what I'm setting it to, but it's actually _O_WTEXT - UTF16 (translated) , (the descriptions are taken from the comments next to the defines in fcntl.h . Trying to manually fwrite a BOM to stdout does nothing. I've tried this and this , but nothing changed. Does anyone have any ideas what this could be? My best guess is that the operating system is just forgetting to set some stuff up correctly and the _setmode call is not going through correctly.
