# Handing OAuth2 refresh token race conditions

- 来源：Stack Overflow
- 链接：https://stackoverflow.com/questions/78406177/handing-oauth2-refresh-token-race-conditions
- 发布时间：2024-04-30

## 正文
We're implementing a 'BFF' (Backend for Frontend) pattern for our application, which is a recommendation from the draft-ietf-oauth-browser-based-apps . One complication we're running into is handing OAuth2 refresh. It's not uncommon for us to have 2 request running almost in parallel. If the access token in this case is expired, they might both try to initiate a refresh, which means the first request wins. There's a few ways to address this: Optimistically refresh the token before it expires. The issue with this is that we need to maintain a ton of state for every active session. Creating a locking system. Not super easy when assuming there's multiple instances of a backend. Loosen the single-use requirement of the refresh token, so multiple parallel requests can all succeed. This feels somewhat dangerous. I'm curious if there's any known best practices around this
