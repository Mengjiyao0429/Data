## 正文
I believe I have made an error when inserting some data into a SQL table. The column containing the error has a datetime timezone aware type, which for Postgres is timestamptz . Here is an example data: 2023-10-24 00:00:00.000 +0100 It was created from a date, without time or timezone information. This is why the time has defaulted to 00:00:00.000 , and the timezone information appears to have defaulted to BST ( +0100 ) either because this is being picked up on the database server side, or on the client side, both machines presumably having change timezone last month. Aside: Why do I know this is an error? I realized that it isn't obvious from my question why this is an "error". As others have pointed out in the comments, there is actually an additional factor at play here, which I was not previously aware of. Applications such as DBeaver have timezone translations embedded into them. By default my DBeaver instance has its timezone set to Europe/London . This is important to be aware of (I was aware of it) but it is a red herring. The real issue is that the client application logic is broken. At the present time I don't fully understand why and I need to investigate further. What is happening? The expected behavior is that the client inserts some data into a database. The data is a timeseries. Each entry to the table has multiple columns. Any one of those column values could change over time. What the client application does is to select all rows from the database with a particular unique identifier code. All rows with the same unique identifier correspond to the same timeseries. Each row has a "first seen" and "last observed" datetime. This defines a window for which the data in the row is valid. If it changes, a new row is inserted with a new "first seen" datetime/timestamp. It orders those rows by "first seen" datetime, and selects the latest row. It compares the current observed column values with the values from this row. If they are the same the "last observed" datetime is moved forward to the current timestamp. If they differ a new row is inserted with the new values and the "first seen" datetime is set to the current timestamp. This is not working as expected, because for the column containing the "day" values which are converted to a datetime, and represented in the client code as a datetime value, the client reports that some rows differ only by this column, and the values differ by 1 hour. All the values should have a time value of midnight UTC 00:00, but they do not. Some are off by 1 hour. How can I fix this? (I have fixed the client side code already.) To "fix" it, the following steps would be required: update rows which have timezone which is not +00:00 . set the timezone information back to +00:00 since only the date information was initially relevant, the time should not change, all time values should remain 00:00 I tried this: alter table my_table add column date_new timestamptz; update my_table set date_new = date_column at time zone 'UTC'; It did not change the displayed value. Neither the timezone displayed value nor time displayed value changed. I considered performing some "hack" using string conversions and string manipulation, but suspect this is probably not the most straight forward approach. I should note that I would like to keep the time and timezone information. In other words, I do not want to convert the datetime column to a date column.
