# 智能体「没报错却少了工具」：怎样接非致命降级通道？

- 来源：阿里云开发者社区 https://developer.aliyun.com/article/1781072
- 发布时间：2026-11-09
- 热度：浏览95

## 正文

现有软件接入智能体 SDK 后，最容易被忽略的一类事故不是 401、429 或余额不足，而是：会话创建成功了」，界面也没弹红字，但工具突然变少、裁决人悄悄缺席、能力位解析失败却回落到「零能力档」——用户和值班同学都以为「还能聊」。 若宿主只接硬失败、不接非致命通报，运维会把「静默降级」当成正常成功。

2025 年末到 2026 年，智能体安全与可观测材料把「看不见的降级」推到开发者面前。OWASP Gen AI《OWASP Top 10 for Agentic Applications》发布说明（页面现行，本机 2026-11-09 再核 HTTP 200；配套 Version 2026 PDF 同站可下载）强调：缺少对智能体在做什么、为何做、调用了哪些工具的清晰可见性时，过度自治会悄悄扩大攻击面，并把小问题放大成系统级故障——强可观测性成为不可妥协项。OWASP Agent Observability Standard 提案 #73（HTTP 200）进一步指出：仅靠单次追踪无法发现随时间发生的静默劣化；点检通过不代表行为轨迹稳定。AWS Well-Architected Agentic AI Lens · AGENTOPS05-BP02（HTTP 200）要求为智能体建立行为基线，监测工具选择漂移、完成率与异常模式，避免只靠静态阈值漏掉「慢慢变差」。同一时期，诊断面也在补齐：Hermes Agent PR #89217（HTTP 200）为 hermes doctor 增加只读的配置组合诊断与稳定 JSON；deepagents dcode doctor（HTTP 200）把安装健康、SDK／平台版本与配置路径打成可粘贴报告；agentdx（HTTP 200）把 Silent Degradation 列为可检测的运维病理之一。上述材料共同回答的行业问题是：硬错误通道不够；装配期／运行期的非致命降级必须有结构化出口，并进入界面与值班链路。

对接入 SDK／会话宿主的开发者，完整行业答案可以收成六句话：

「请求成功」≠「能力完整」：会话能聊、轮次结束，仍可能发生工具裁剪、裁决人降级或装配告警。
静默降级是一等运维对象：行业安全／可观测材料已要求看见工具调用与行为漂移，而不是只盯 HTTP／异常栈。
非致命通报不要丢进 console：应进入宿主回调或会话事件流，再投影到 UI／日志／告警；缺席回调不等于「没事」。
回落策略必须可解释：例如能力段解析失败时回落「零能力」而不是「缺省放开」，这是安全取向，但必须让人知道发生了回落。
硬失败与 notice 分通道处理：401／429／capability_disabled 走错误排障；sdk.notice／warning 走降级可见性，不要混成同一种「失败 toast」。
装配前预检与运行期通报互补：CI／本地 doctor 类命令抓阻断配置；运行期 warning 抓会话装配中的非致命事实。

本文把上述行业问题映射到已核实的 Tansr 机制：createSession({ onPlatformWarning })／onWarning 接收 bundle 解析与装配期的非致命事实；缺席时回落会话事件流 turn.error { scope: 'sdk.notice', recoverable: true }——文档原文写明恒不写入 console、恒不改装配结果；常见码含 app_platform_mismatch、tools_platform_deprecated、capabilities_unparsed（SDK 0.13.0 起回落零能力档 tools 全 false，不再回落缺省档）以及多项 adjudicator_*。依据见 平台装配与 bundle、PlatformWarning、会话与事件流（本机 2026-11-09 再核均为 HTTP 200）。命令行侧可用 设置与 doctor 的 tansr doctor／--json 做零网络装配预检（退出码只看 problems 四类阻断码）。它不是 S06 的 401／429／余额／能力关闭硬失败分码排障全文，也不是 S07 能力位治理决策稿、P01 权限审计链、S10 统一面完成判定，或 S08／S09／S01／R01；这里只回答：宿主怎样把「没报错的降级」接出来，并与硬失败分流。

直接答案
接 onPlatformWarning（或全量 onWarning）：在 createSession 时传入；把 code／message（及全量通道的 detail）写入应用日志与可选 UI 条，不要只 console.warn 后丢掉。
同时监听 turn.error 且识别 scope: 'sdk.notice'、recoverable: true：这是回调缺席时的回落通道；不要把它当成与硬失败同一套「重试／中断」策略。
按码分流用户可见性：capabilities_unparsed → 明确提示「能力配置解析失败，已按零能力装配」并引导修 bundle
