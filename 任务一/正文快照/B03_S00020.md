# RAG 进阶地图：Self-RAG、CRAG、GraphRAG、Agentic RAG 到底有何不同？

## 正文

引言：名字很唬人，但逻辑其实很清晰

检索增强生成（RAG）已经从"向量检索 → 拼 prompt → LLM 生成"的朴素形态，演化出一批听起来很高大上的范式：Self-RAG、CRAG 、GraphRAG、Agentic RAG。名字一个比一个唬人，但如果只背名字、讲不清它们各自解决什么问题，那么无论是在技术选型还是在面试中，都很容易露怯。

其实，这四种范式的诞生逻辑非常清晰——它们分别对应朴素 RAG 的三个致命痛点：

检索质量参差不齐：用户的提问方式千变万化，但系统不会区分检索结果的好坏，一律喂给 LLM，结果就是 LLM 在低质量上下文上"一本正经地胡说八道"。
所有问题走同一套流程，太死板：有些问题根本不需要检索（比如"1+1 等于几"），有些复杂问题却需要多轮检索，而朴素 RAG 一律只检索一次。
知识库覆盖有盲区：知识库里永远不可能有所有答案，当找不到相关内容时，朴素 RAG 要么让 LLM 编造答案，要么返回一个风马牛不相及的回答。

理解了这三个痛点，再去看四种高级范式，就会发现它们各自瞄准了一个具体的问题，而不是凭空造出来的名词。

先铺一层：RAG 的三代演进

在讲四种范式之前，有必要先建立一条演进的参照线。RAG 大致经历了三代：

Naive RAG：最直白的"检索 + 生成"，什么都不优化，召回什么送什么，幻觉和偏差就是从这里来的。
Advanced RAG：在检索前加 Query 改写和扩展，在检索后加 Rerank 精排和内容压缩。工程改动小、效果提升明显，是当前大多数生产系统的默认形态。
Modular RAG：不再在固定流程上打补丁，而是把各环节拆成可独立替换的模块，像乐高一样按需组合，LlamaIndex 的 Workflow 和 LangGraph 都是这个设计思路。

这里有一个关键认知：Advanced RAG 远不是终点，它有一个隐含假设——流程是固定的。而真正的复杂场景，需要的是"流程本身能根据情况调整"。四种高级范式，正是在这个"灵活组合"的思路上，针对特定痛点做了更深度的设计。

Self-RAG：LLM 自己决定"要不要检索"

Self-RAG 专门解决第二个痛点——“所有问题都走同一套流程，太死板”。它的核心思想是让 LLM 成为一个能自主决策的智能体 ，通过训练让模型学会使用四种特殊的"反思 token"（reflection tokens）：

Retrieve token：当前问题到底需不需要检索？
Relevance token：检索回来的内容和问题相不相关？
Support token：生成的答案有没有文档支撑（用来防幻觉）？
Utility token：最终答案对用户有没有用？

它的执行流程是：先判断要不要检索（常识问题直接答）→ 检索后逐条评估每个 chunk 的相关性，不相关的直接跳过 → 基于相关 chunk 生成候选答案 → 对每个候选答案打分（有没有文档支撑、对用户有没有用）→ 综合选出最优答案。

这里有一个很容易被忽略的前提：那四种反思 token  不是现成 LLM 自带的，需要在专门构造的数据集上对基础 LLM 做监督微调 ，把特殊 token 作为新词表的一部分训练进去。换句话说，Self-RAG 不能拿一个普通的 GPT-4 直接"套用"，要么用论文开源的微调版本（基于 Llama2-7B/13B），要么自己造数据做微调。

这也是它和 CRAG、Agentic RAG 最不一样的地方：后者都可以在通用 LLM 上直接跑，而 Self-RAG 需要特殊训练的模型，工程门槛更高。它的好处也很直接——不需要检索的问题直接回答，省了开销；检索结果不相关时能识别出来，避免了基于错误上下文的幻觉。

CRAG：检索质量差时，自动降级兜底

Self-RAG 解决的是"要不要检索"，那如果检索了、但结果质量很差怎么办？这就是 CRAG（Corrective RAG）要解决的问题，对应第三个痛点——知识库覆盖有盲区。

CRAG 在检索完之后加了一个质量评估环节，然后做三级路由决策：

判定"相关"：直接用本地知识库的结果生成答案。
判定"不相关"：说明知识库没有覆盖这个问题，丢弃本地结果，降级走网络搜索。
判定"模糊"：把本地结果和网络搜索结果合并，两者互补使用。

这个质量评估器可以是专门训练的轻量级分类模型，也可以用 Rerank 模型的分数来近似。具体的判断阈值需要根据业务场景来调，没有固定数值，核心思路是让系统能自动识别"检索结果靠不靠谱"，并做出相应的降级决策。

CRAG 的核心价值在于"兜底"：知识库覆盖不到的问题不会直接乱答，而是自动去网上找答案，大幅提升了系统的健壮性。它把知识库当主力、把网络搜索当备胎，两者配合使用——这是很多人忽略的一点：RAG 系统不一定只能用本地知识库回答问题。

GraphRAG：用知识图谱补上"全局理解"的短板

Self-RAG 和 CRAG 解决的都是"检索策略"层面的问题，但还有一种瓶颈来自检索方式本身的局限。普通的向量检索 本质上是在做"一对一匹配"——用一个 query 向量去和一个个 chunk 向量比距离，它擅长找到和问题直接相关的局部片段，却无法理解整个知识库的宏观结构和跨文档的关联关系。对于"这批文档的核心主题是什么""A 公司和 B 公司之间有什么关联"这类需要全局视角的问题，单纯向量检索会失效。

GraphRAG 就是微软针对这个问题给出的方案，论文《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》于 2024 年发布，同年开源了代码。

它的核心做法分两步。预处理阶段，先用 LLM 从文档里抽取实体和关系，建成知识图谱，然后用 Leiden 等社区发现算法对实体做聚类，把紧密关联的实体分成一个个"社区"，再对每个社区生成一份 LLM 摘要，描述这个社区里的实体之间是什么关系、整体在讲什么。这些社区摘要会形成多层层次结构，从细粒度到粗粒度都有覆盖。

检索阶段，GraphRAG 支持两种查询模式：对于局部问题（“A 公司的 CEO 是谁”），直接在知识图谱中做实体查找和关系遍历；对于全局问题（“这些文档的主要主题有哪些”），则用 Map-Reduce 的方式，先让 LLM 分别阅读各社区的摘要提取相关信息，再汇总生成最终答案。这种"社区摘要 + Map-Reduce"的设计，是 GraphRAG 区别于普通知识图谱方案的核心创新。

它的价值在于把全局信息提前"蒸馏"好了，查询时不需要遍历所有文档就能回答全局性问题，适合知识关联性强、需要全局视角的场景，比如金融领域的企业关系分析、医疗领域的药物-疾病-症状关联查询、大规模文档集的主题归纳。代价是构建知识图谱和社区摘要需要大量 LLM 调用，预处理成本较高。

Agentic RAG：把 RAG 做成一个会循环的智能体

前面几种范式虽然各有创新，但流程的步骤大多是预先定义好的，最多是根据条件做分支选择。可有些问题复杂到连"需要检索几次""每次检索什么"都无法预先定义，需要 LLM 根据中间结果动态决定下一步——这就是 Agentic RAG 的用武之地。

Agentic RAG 把 RAG 嵌入 Agent 循环，LLM 可以自主决定：要不要再检索一次、用什么关键词检索、检索结果是否足够、什么时候可以生成最终答案。它的执行流程是：

接收问题，进入循环；
LLM 根据当前已收集的上下文判断"信息够了吗？如果不够，下一步该搜什么关键词？"；
按 LLM 指定的关键词检索，把新召回的 chunk 追加到已有上下文；
每轮重新评估"现在能回答了吗"，不够就继续检索，够了就生成答案；
为防止死循环，设置最大迭代次数兜底。

这套机制特别适合需要多步骤推理的复杂问题，比如"帮我分析 A 公司最近三年的财报，找出营收增速放缓的根本原因"——这类问题需要多次、有针对性地检索不同维度的内容，一次检索完全不够。

和前面几种范式相比，Agentic RAG 最大的区别在于流程不是写死的，而是 LLM 在运行时自己决定。如果说 Self-RAG 是给 RAG 加了一个"要不要检索"的开关，CRAG 是加了一个"检索不好怎么办"的兜底，那 Agentic RAG 是把整个检索流程变成了一个可以不断循环、不断调整的智能体。

四种范式对比与选型

把这四种范式横向对比一下，选型时心里就有谱了：

范式	解决的核心问题	核心机制	适用场景	工程复杂度
Self-RAG	不是所有问题都需要检索	训练反思 token，LLM 自主决策	问题类型多样、部分不需检索	高（需特殊训练模型）
CRAG	检索质量差时怎么办	质量评估 + 三级路由降级网络搜索	知识库覆盖不全的场景	中
GraphRAG	全局理解和跨文档关联	社区发现 + 层次摘要 + Map-Reduce	实体关系复杂、需全局视角	高（图构建成本大）
Agentic RAG	复杂问题需要多轮动态检索	把 RAG 嵌入 Agent 循环	复杂多步骤问题	中（Agent 框架）

选型时不要看名字高级不高级，而要看业务的主要矛盾：如果只是检索召回一般，先做 Advanced RAG；如果本地知识库经常答不上来，优先做 CRAG；如果用户问的是关系和全局总结，考虑 GraphRAG；如果问题天然需要多轮检索和工具调用，再上 Agentic RAG。生产系统里往往也不是只用一种，两三种组合是常态。

结语

回到最初的问题：Self-RAG、CRAG、GraphRAG、Agentic RAG 到底有什么区别？一句话概括——它们不是竞争关系，而是分别补上了朴素 RAG 的一块短板：Self-RAG 管"要不要检索"，CRAG 管"检索不好怎么兜底"，GraphRAG 管"局部检索搞不定的全局理解"，Agentic RAG 管"复杂问题的一次检索不够用"。理解了每个范式背后的痛点，就不会再被这些名词绕晕了。
