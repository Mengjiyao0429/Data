# Spring AI MCP MVC (1.1.2) with Streamable HTTP on Kubernetes: How to handle MCP sessions across multiple replicas?

## 正文
I'm using Spring AI MCP MVC version 1.1.2 and deploying my MCP server on Kubernetes with multiple replicas (2 instances). The MCP server uses the Streamable HTTP transport. The issue is that when an agent connects, it first initializes a session. The MCP server returns an Mcp-Session-Id , and subsequent requests (tool discovery, tool invocation, etc.) must include this session ID. However, in a multi-instance deployment, the session is only recognized by the instance that originally created it: Agent sends initialize request. Replica A handles the request and returns Mcp-Session-Id=abc123 . Later, the agent sends a tool call with Mcp-Session-Id=abc123 . Kubernetes load balancing routes the request to Replica B. Replica B does not know about session abc123 , and the request fails. So the MCP session becomes instance-local, which causes problems in a horizontally scaled deployment. My questions are: Is there a recommended way to run Spring AI MCP MVC with Streamable HTTP in a multi-replica Kubernetes environment? Should the MCP session state be externalized (e.g., stored in Redis) so that all replicas can access the same session information? Does Spring AI MCP MVC provide any built-in mechanism for distributed session management or shared session storage? Is the preferred solution to use sticky sessions at the ingress/load balancer level, or is there a better approach? Are there any best practices for production deployments of MCP servers using Streamable HTTP? Environment: Spring AI MCP MVC: 1.1.2 Transport: Streamable HTTP Deployment: Kubernetes Replicas: 2+ Load balancing Service / Ingress
