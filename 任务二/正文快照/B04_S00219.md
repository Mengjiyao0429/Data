## 正文
I have a .NET 8 application running on multiple instances. Each instance consumes messages from the same queue. The queue provides at-least-once delivery, so the same message can occasionally be delivered to two application instances at nearly the same time. I need to ensure that each message is processed only once. I currently store the message ID in a SQL Server table before executing the business logic: public class ProcessedMessage { public Guid Id { get; set; } public DateTime ProcessedAtUtc { get; set; } } The Id column is the primary key. My current implementation is: public async Task HandleAsync( OrderCreatedMessage message, CancellationToken cancellationToken) { var alreadyProcessed = await dbContext.ProcessedMessages .AnyAsync(x => x.Id == message.MessageId, cancellationToken); if (alreadyProcessed) { return; } dbContext.ProcessedMessages.Add(new ProcessedMessage { Id = message.MessageId, ProcessedAtUtc = DateTime.UtcNow }); await CreateOrderAsync(message, cancellationToken); await dbContext.SaveChangesAsync(cancellationToken); } The problem is that this check is not atomic. Two application instances can execute AnyAsync() at the same time, both receive false , and both execute CreateOrderAsync() . One of the SaveChangesAsync() calls eventually fails because of the primary key constraint, but by that point both instances may already have performed the business operation. I considered wrapping everything in a transaction: await using var transaction = await dbContext.Database.BeginTransactionAsync(cancellationToken); var alreadyProcessed = await dbContext.ProcessedMessages .AnyAsync(x => x.Id == message.MessageId, cancellationToken); if (alreadyProcessed) { await transaction.RollbackAsync(cancellationToken); return; } dbContext.ProcessedMessages.Add(new ProcessedMessage { Id = message.MessageId, ProcessedAtUtc = DateTime.UtcNow }); await CreateOrderAsync(message, cancellationToken); await dbContext.SaveChangesAsync(cancellationToken); await transaction.CommitAsync(cancellationToken); However, with SQL Server's default READ COMMITTED isolation level, both transactions can still read that no record exists. I also considered: Using SERIALIZABLE Inserting the message record first and catching the unique-key exception Using sp_getapplock Adding a distributed lock Using a separate inbox table Retrying the entire transaction through EF Core's execution strategy The business operation only modifies the same SQL Server database, so it can participate in the same transaction. There are no external HTTP calls in this particular handler. My requirements are: Only one application instance should execute the business logic for a given MessageId A failed handler must be retryable A message must not be marked as successfully processed if the business transaction rolls back The solution should work across multiple application instances I would prefer not to introduce Redis or another distributed-locking system if SQL Server can provide the required guarantee What is the recommended pattern for implementing this atomically with EF Core and SQL Server? In particular, should I: Use a SERIALIZABLE transaction around the existence check, insert and business logic? Attempt the insert first and use the primary-key constraint as the concurrency mechanism? Use a different SQL Server or EF Core pattern entirely? I am also interested in how this should interact with EF Core retrying execution strategies, since manually created transactions require the entire operation to be executed through CreateExecutionStrategy() . Environment: .NET 8 EF Core 8 SQL Server Multiple application instances Queue with at-least-once delivery
