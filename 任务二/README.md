# 任务二：AI 应用机会判别与归类

第三届甘肃省大学生数据挖掘挑战赛（本科组）赛题《AI 应用场景的智能挖掘与机会评估系统》。
本文件夹完整保存任务二的目标、方法、所用数据、结果与全部源码，可直接复现。

> **本版对应任务一更新后的数据集：8038 条记录、8 个批次（B01–B08）、14 个来源。**
> 上一版基于 329 条的旧结果已被本版替换。

## 一、任务目标

对**任务一同一批次的全部清洗记录**逐条判断是否构成“AI 应用机会”（1/0）并输出 0~1 机会置信度；
对判为机会的记录，依据附件1 标签体系各标注**一个功能类别**与**一个所属行业**。非机会记录同样保留在结果中。

判定依据（赛题四条规则）：

| 维度 | 核心问题 | 本项目做法 |
|---|---|---|
| ① 真实需求 | 是否有明确用户/业务场景与可观察需求信号 | 需求信号词 + 业务场景锚定；**设前置门槛 R≥0.30**；开发者工程报错、新闻体裁、供给侧资产大幅衰减 |
| ② AI 是核心 | AI 是否是解决问题的核心手段 | 成熟 AI 能力词（中英双语）；仅出现“AI”字样只给弱证据 |
| ③ 技术可落地 | 能否用现有成熟 AI 能力实现 | 公开 API/SDK、开源预训练模型、轻量适配证据；自研/基础模型供给打折或排除 |
| ④ 排除情形 | 是否属纯科普教程/广告/AI 营销噱头 | 命中即直接判 0；另单列“开发者组件/工具供给”“模型供给”两类供给侧排除 |

置信度 = 0.36·R + 0.26·A + 0.22·F + 0.16·Q，再乘 (1 − 0.35·E)（E 为排除强度），阈值 0.50（按 116 条人工标注集的阈值敏感性分析，由 0.56 校准到 0.50，偏向召回）。
论文中明确其为**规则证据评分**，不是经统计校准的后验概率。

## 二、完成结果

- **result2.csv：8038 行，与任务一批次/编号完全对齐，无缺失、无重复、顺序一致。**
- 判为机会 **986 条**（12.3%）：

  | 批次 | 记录数 | 机会数 | 机会率 | 来源构成 |
  |---|---|---|---|---|
  | B01 | 1233 | 43 | 3.5% | GitHub |
  | B02 | 1233 | 57 | 4.6% | GitHub |
  | B03 | 1232 | 46 | 3.7% | GitHub |
  | B04 | 1256 | 171 | 13.6% | Stack Overflow |
  | B05 | 563 | 71 | 12.6% | CSDN / IT之家 / 36氪 / 阿里云 / InfoQ / 量子位 等 |

- 机会置信度区间 [0.5063, 0.9460]，非机会区间 [0.0100, 0.4900]，**置信度与判定完全一致**。
- 判 1 记录均有一个合法功能类别与一个所属行业（均取自附件1）；非机会记录不填标签。
- 人工标注集 116 条（正 30 / 负 86）评估：**Accuracy 0.845、Precision 0.630、Recall 0.967、F1 0.763**；
  功能类别一致率 60.0%（18/30）、所属行业一致率 63.3%（19/30）。
- 连续两次运行 `result2.csv` 逐字节一致（SHA-256 稳定），可复现。

## 四、数据说明

1. **输入未改**：`原始数据/任务一输出/result1.csv` 与任务一产物逐行一致（8038 条），
   任务二只读取，未修改批次号、记录编号、来源、链接等任何字段。
2. **新版表头已适配**：任务一更新后热度拆分为 `星标数/浏览数/点赞数/评论数/收藏数` 五列，
   读取逻辑按列名取值，同时兼容旧版单列“热度指标”。
3. **快照格式已适配**：新版快照为 `# 标题 - 来源：… - 链接：… - 发布时间：… - 热度：… ## 正文 …`，
   判别时剥离标题行中的元数据，只将“## 正文”之后的内容作为判别文本。
4. **高星标记录的核实（结论）**：B01–B03 的 GitHub 记录中有 19 条“星标数”超过 10 万
   （最大 465033，如 `morluto/rea`）。经 `api.github.com/repos/<owner>/<repo>` 逐条核对，
   这些数值与平台实时数据一致（如 browser-use 121292、firecrawl 202522、obra/superpowers 319036、
   morluto/rea 465507），**属真实值而非采集异常**，无需修改。任务二未使用星标数作为判别依据。

## 六、如何验证真实性

1. 打开 `结果/result2.csv`，任取一行的“采集批次号-记录编号”，可在 `原始数据/任务一输出/result1.csv` 中找到。
2. 用记录编号在 `正文快照/` 找到对应正文，与 `task2_evidence.jsonl` 中的“判别文本”“证据关键词”对照，
   即可核对判 1/0 的依据。
3. 功能类别、所属行业均能在附件1 的 16 类 / 30 类中找到，无自造标签。
4. 置信度由固定公式计算，同一条记录重复计算得到相同数值。

## 七、已知局限（如实说明）

- **开发者技术问答**：Stack Overflow 中“报错求助”与“业务需求”的边界仍有混淆，是误报的主要来源之一；
  已加入“工程问题需求信号打折”规则，但仍无法完全区分。
- **开源项目描述极短**：B01–B03 的 GitHub 描述中位长度约 200 字符，多为“一句话产品定位”，
  缺少痛点表述，导致这三批机会率偏低（3.5%–4.6%），并不代表这些项目没有价值。
- **开发者工具/框架**：按“面向工程师复用、非终端业务需求”排除，属口径选择，论文中有说明。
- **行业“其他”占比高**（753/986）：这是“证据不足不硬派行业”的主动原则。
- 人工标注集仅 116 条，属小样本评估，指标应表述为“同一标注集上的规则评估”，不是泛化性能。
